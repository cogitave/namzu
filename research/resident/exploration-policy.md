# Evaluating a model-proposed exploration policy

2026-09-14, base `63940108`. The previous [discovery experiment](autonomous-learning.md)
demonstrated acquiring task knowledge from self-selected experiments, but kept
the exploration procedure fixed. This study asks whether a model-generated change
to that procedure improves acquisition in fresh environments at equal limits.

## Research and implementation

[HyperAgents](https://arxiv.org/html/2603.19461v1) distinguishes changes to task
agents from changes to the mechanism producing future improvements. Its
[pinned generation loop](https://github.com/facebookresearch/HyperAgents/blob/8172fedda690dcc8347996fd12da2fdc9bb098a3/generate_loop.py)
keeps a frozen meta-agent copy for its no-self-improvement comparison and applies
inherited lineage changes separately. This motivates a frozen acquisition-policy
control and measurement of later learning, rather than counting a stored skill
as improved learning ability. Namzu is not implementing its full editable program
or inheriting its reported results.

[GEPA](https://arxiv.org/abs/2507.19457v2) proposes prompt changes using execution
feedback. In its [pinned reflective proposer](https://github.com/gepa-ai/gepa/blob/ef525a44626a725b6987a35b4a75e36fbfaf0e25/src/gepa/proposer/reflective_mutation/reflective_mutation.py),
proposal generation/evaluation and engine acceptance are separate. Namzu reuses
its existing independent evaluation and preservation gate. It does not introduce
a GEPA dependency or claim a Pareto search implementation. The prior
[source manifest](results/2026-09-14-autonomous-learning-sources.json) pins inspected
author code, including byte hashes.

The reusable kernel addition is a purpose on learned guidance and its learning
cycle: `task` or `exploration`. The host captures it before generation. Content
hashes bind exploration purpose; generation and direct promotion cannot repurpose
an existing named skill. Ordinary resident context, its catalogue and skill-read
tool withhold exploration policies. Hosts explicitly project a policy into an
explorer. Source freshness, size caps, accounting and rollback still apply.
See the [public contract](../../docs/sdk/exploration-policies.md).

## Predeclared protocol

One Muse-low proposal receives the previous real cold failure and tool trajectory,
the frozen baseline policy, measured prior results and a new acquisition budget.
It receives neither a handwritten improved policy nor new environment constants,
answers, test records or evaluator code. It may change only the explorer's
instruction text. Model weights, tool code, predictor, evaluator and acceptance
logic stay fixed. The proposed text is retained unchanged even if poor.

Each evaluation episode constructs a fresh service with three record kinds,
identifier, date and sealed status. Namespace and kind aliases differ per episode.
Five rule families retain month, day or year components, or implement simpler
identifier-only and kind/identifier services. The latter two are predeclared
preservation tasks, not newly recovered tasks relabelled as controls.

Verification and confirmation each contain two independently seeded episodes per
family. Both arms receive the same environment and limits: at most eight preview
records, six explorer iterations, 16,000 explorer tokens and 120 seconds. A separate
fresh predictor gets only actual successful tool observations and six withheld
records, with one iteration and 12,000 tokens. It receives neither policy text nor
the explorer's final narrative. Tool failures remain in the original transcript
and usage totals. This measures the value of acquired observations to a fixed
downstream model. It is not a comparison against a cold model denied exploration.

Arm order alternates per episode. All six exact destinations and normal settled
completion are required for an episode pass; per-record scores are also retained.
Both arms and all failures are charged to the same 1,500,000-token study allowance.
Unknown usage stops the study without replacement runs. These limits are explicit
experiment settings, not new application defaults. Fresh confirmation is admitted
only if verification passes the existing gate; failure does not justify retrying
until a successful run appears.

If accepted, the policy is reopened from the agenda, explicitly projected for
exploration, and tested on three new environments. Rollback repeats those three
environments in fresh sessions using the frozen baseline policy. A rejected or
inconclusive candidate remains journaled and inactive; there is then no accepted
policy to roll back. Generation cannot replace protection or assign new authority.

## Results

The live proposal was generated by Muse low and retained unchanged. It recommends
an anchor, single-factor sweeps and interaction checks. There is already a weakness
in that text: its advertised four-to-five-record sweep lists six individual
variations. It has not been corrected by hand or accepted as reliable guidance.

The live comparison is **inconclusive due to provider rate limiting**. Only one
episode has normal completions on both sides: each predicted 5/6 destinations
correctly and returned `UNKNOWN` for the final sealed-notice case. Both used eight
preview records. The proposed policy then predicted 6/6 in another episode, but
the matching baseline was rejected by Zen with HTTP 429. That unpaired success
cannot establish a policy improvement.

The retained study contains 41 SDK runs: seven normal completions (one proposal,
three explorer/predictor pairs), fifteen provider-error runs carrying HTTP 429,
and nineteen cancelled runs. The original study driver continued creating empty
cases after errors and then after an operator SIGINT; the SDK stopped cancelled
runs before useful execution, but the driver should not have advanced. All those
attempts remain in the evidence. The machine totals of 0/10 versus 1/10 include
unavailable/cancelled cases and are **not a valid accuracy comparison**. The
independent audit separately identifies the sole comparable pair.

Known study consumption is 38,459 tokens, with no unresolved token receipts in
those returned runs. The seven generated runs have unknown prices; zero-valued
cost fields are not a verified free-service result. The cycle ended `cancelled`,
its retained review was `inconclusive`, and no policy was activated. Confirmation
and live reopening/rollback were not performed.

This exposed a study-driver defect, now fixed: a non-normal model run ends the
study after retaining its receipt, before a predictor or later episode starts.
Failed, cancelled and inconclusive cycles also return a nonzero process exit code.
A controlled CLI run injected a provider 429 at the first explorer and verified
exactly two retained runs (proposal and failed explorer), no prediction/evaluation,
no active policy, and exit code 2. A separate complete scripted control verified
both acceptance rounds, explicit-purpose projection, reopening 3/3 and rollback
0/3. These controls establish execution behavior, not learned performance.

The first development control mistakenly scripted successful rollback predictions;
that control was invalid and its summary is retained. A corrected control completed
before live execution. After the live driver fix, both complete and provider-fault
controls were run again. No second live study or substitute successful sample was
run after throttling. Original live source bytes were saved and checked against
their predeclared hashes before changing the driver.

The built TUI was exercised in a 120×34 PTY with a separate home. Muse started the
study as one background command after one exact approval and read the running job
without another approval. The exit notification appeared between turns and `/jobs`
reported it. The old study's exit 0 meant the process ended, not that its learning
cycle succeeded; the driver fix above addresses that mismatch. A single later
request to read the result received a clear `provider.rate_limit` message and no
tool ran. This verifies the current rate-limit display, while the cause of the
previous study's empty/unsettled observer reply remains unproven; it must not be
retroactively labelled the same HTTP failure.

## Reproduction

Build the repository, then prepare without inference:

```sh
node research/resident/exploration-policy-study.mjs --prepare --live
```

Run the exact command it prints once, directly or as a background job from the
built Namzu TUI. It uses a separate temporary workspace and application home,
the CLI's real `resident learn` command and SQLite journal. Keep the parent TUI
open until its job exits. Omit `--live` for an explicitly scripted plumbing control;
its candidate and predictions are hardcoded and establish no learning result.
`--prepare --control-provider-error` creates the scripted failure control. It cannot
be combined with `--live`. Do not resume the cancelled live batch or fill its missing
measurements with new calls; prepare a separately identified experiment when the
provider is available, and retain the original outcome.

```sh
node research/resident/exploration-policy-study.mjs --inspect /absolute/study/root
node research/resident/exploration-policy-audit.mjs /absolute/study/root
```

This is a single proposed change to an exploration prompt in related synthetic
services. Even a positive result would not demonstrate open-ended recursive
self-modification, unsupervised grading of arbitrary user work, model training
or AGI. Host-provided tools and grading still define the experiment. Sustained
improvement requires further generations and untouched task families, with every
unsuccessful proposal retained and compared at equivalent resources.
