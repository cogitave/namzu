# Pal delivery and communication goal

Status: active. Updated 2026-10-02 after the operator's channel and Windows
steering. This checklist records the working plan for the active Goal; a checked
source inspection or fixture test is not a claim that its deployment works.

## Accepted scope

- One SDK Pal identity and runtime used by CLI and desktop.
- Each Pal must have an actual local virtual computer with its own persistent
  browser/profile and filesystem. A host control directory is not that computer.
- Finish the individual Pal MVP before Team/Coordinator and organization views.
- Pals must be able to exchange messages and subscribe to authorized actions and
  activity, independently of ephemeral subagent/task messaging.
- The same identity should work through channel adapters, including Microsoft
  Teams. Channel transcripts/audiences remain separate from Pal Team membership.
- Research OpenDots, Channels source and the operator's Happy reference. Borrow
  architectural ideas where verified; add no other agent SDK dependency.
- Audit Windows host commands, PowerShell/CMD selection, quoting, cancellation,
  output and UI events against current Codex source. Linux guest Bash is a
  separate execution environment and must not be converted to a host command.
- No new push/publication authorization. Screenshots of Happy remain private;
  navigation and inspection do not authorize messages or account changes.

## Ordered work

1. **Complete the existing MVP change.** Saved revisions, conversation ownership,
   pinned profiles, mandatory computer admission, own guest tools, terminal
   new/resume, desktop onboarding/context, explicit setup errors and lifecycle.
2. **Verify and commit the foundation.** Scoped tests, workspace gates and native
   Windows checks. Real guest smoke needs a local engine and built image; current
   fixtures and source validation do not satisfy that gate.
3. **Inspect reference behavior and routes.** Read the signed-in Happy pages;
   pin source commits for OpenDots, Channels and Codex. Record observed behavior,
   shipped contracts and inference separately.
4. **Write the communication decision.** Map current directory/inbox/channel/
   workflow/scheduler primitives. Specify principal and thread identity, routing,
   authorization, transcript isolation, deduplication, replay/cursors, busy-turn
   delivery, wakeup, activity publication and approval correlation.
5. **Implement verified gaps in Namzu.** SDK ports/storage/contracts first;
   CLI and desktop adapters afterward. Team coordination and external transport
   configuration must not grant implicit access to another Pal's private state.
6. **Exercise failure and recovery.** Two Pals/processes, busy and idle delivery,
   duplicate/replayed events, permission revocation, stale actions, restarts,
   native Windows shells and corresponding renderer event ordering.

## Current deployment prerequisite

Docker is absent in the Linux environment and normal Windows installation.
An existing native Windows Podman installation and its stopped WSL machine were
subsequently found. The existing machine was started for the authorized local
computer exercise without installing a new engine or changing its default
connection. The Namzu guest image was built separately; unrelated containers
were preserved. Actual lifecycle, native TUI and desktop proofs succeeded. The
Windows WSL machine lacks usable cgroup controllers, so this transport does not
claim CPU/memory/PID quotas; Chromium relies on the outer guest boundary rather
than its inner sandbox. Neither limitation is hidden by a host fallback. The
UNC command-cwd regression has passed. Communication/query/channel work remains
active after the foundation commit; Team/Coordinator views remain a later step.
