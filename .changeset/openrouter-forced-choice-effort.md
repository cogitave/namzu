Through OpenRouter, a DeepSeek V4 sub-agent no longer ends with the vendor's HTTP 400 "Thinking mode does not support this tool_choice", and choosing effort `max` or `ultra` no longer throws. The OpenRouter driver leaves a forced tool choice (`required` or a named function) off the request for the models that refuse it while they reason, and when a host answers a forced choice with a 400 that names `tool_choice` it sends the request once more without it (`auto` and `none` are untouched, and a host that accepts the choice still gets it). Effort `max` and `ultra` now send the highest level the model's OpenRouter listing names (`max` for DeepSeek V4.1 Flash), or `xhigh` when the listing cannot be read. `OpenRouterConfig` gains an optional `logger` for the driver's debug lines. In the SDK, a tool choice set by a step (`prepareStep`) is now asked of the provider with `acceptsForcedToolChoiceFor`, as the loop's own forced step already was, and is not sent when the provider says it refuses it. Nothing is removed; a request that used to fail now succeeds. One behaviour changes for any provider that answers `acceptsForcedToolChoiceFor` with `false` (the DeepSeek driver with thinking on, Anthropic models that refuse a forced choice): a `prepareStep` choice of `required` or a named function used to fail the step with the provider's refusal, and is now left off the request, with one line added in words that the reply must be a tool call. A caller that wants the hard failure back checks the choice itself before returning it from `prepareStep`.
