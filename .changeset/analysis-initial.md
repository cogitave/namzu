"@namzu/analysis": minor

First release of `@namzu/analysis`, a native, paged index of JavaScript and TypeScript for agents that read code they did not write. `createCodeAnalysisProvider({ cacheDir })` returns the SDK's `CodeAnalysisProvider`: `index` (incremental by size, mtime and content hash), `findLiteral`, `enclosingFunction`, `functionSource`, `callersOf` and `imports`. Every result is paged, cited as path:line:column with UTF-16 columns (a byte-order mark counts as the first character, as in what `read` shows), and carries what was observed, what was inferred (callers are matched by name text, not scope) and whether coverage is complete. It parses in a child process, so a parser crash on a pathological file (a 6,000-deep array, 100,000 chained terms) costs that file and is reported as partial coverage rather than ending your process; it stops at 20,000 directories or 45 seconds per call and says which narrower path to index next; it never reads through a link or outside its root, even for a file replaced after indexing; and several processes can index one root at once. A host that bundles the package names its own copy of the parsing child with the `hostScript` option, or builds the `@namzu/analysis/indexer-host` export as an entry. Its parsing child gets no environment secrets and runs under Node's permission model, and its cache is trimmed by age and size. It needs Node 22.13 or newer and installs `oxc-parser`. On Node 22.13 to 22.15 SQLite has no FTS5, so `findLiteral` scans instead of using its substring index: same answers, slower, in a separate cache file. To use it, pass the provider to `query({ codeAnalysis })` and mount `getCodeAnalysisTools(provider)` from `@namzu/sdk`.
