A plugin read through the common plugin layout may now name a hooks module in `hooks/hooks.json` (`"modules": ["./mod.js"]`), and the SDK can run it: `startHookModule` runs the module in a `worker_threads` Worker of its own inside a `node:vm` context with no `require`, `process`, timers or network, and returns hooks to attach for the `classic.*` events it registers (`register(on, options)`, globs, negations, matchers, `.catch`, `next`). Its answers are read by the same code as a command hook's JSON, a dispatch fails closed after 10 seconds, and `$` reaches the host through a bridge with limits. `scanHookModule` and `locateHookModule` read a module with `acorn` before it runs; `summarizeHookModule` and `hookModuleConsentEntry` give a consent surface what it does. `PluginLifecycleManager` takes a `hookModuleFor` callback and ends what it started when the plugin is disabled, uninstalled or rolled back; `shellHookInputFor` is exported from the shell-hook adapter's input builder. Nothing existing breaks. What changes for a reader of the layout: `hooks-modules-refused` is no longer raised for the module in `hooks/hooks.json` (it appears as `hooks-module-used`, `hooks-module-scan-refused` or `hooks-module-not-used`); a second module and a `modules` list in any other hooks file are still refused, and so is a `.js` path given directly in the manifest's `hooks`. `acorn` is a new dependency.
