A plugin can ship hook entries, and a plugin written for the common hook contract moves as written. Put them in `hooks/hooks.json` in the plugin folder (read when it exists), in a `.json` path listed in the manifest's `hooks` (any other path in `hooks` is still a JavaScript module), or inline under the new manifest key `hookEntries`, as the events object itself or under a `hooks` key, in either shape. They are read by the same reader a config file's `hooks` key goes through, so problems are said the same way and one bad entry never stops the others; a path that leaves the plugin folder is refused. A command is started with `NAMZU_PLUGIN_ROOT` (the plugin's folder) and `NAMZU_PLUGIN_DATA` (a folder kept for the plugin under the Namzu home, created when first needed, never inside the plugin); a shell command expands them from its environment and an entry in the exec form has them put in its command and arguments. A variable of another tool that ends in `_PLUGIN_ROOT` or `_PLUGIN_DATA` is given the same folders under the name the command used, so a script it starts reads it by that name. The manifest's `hooks` may also be the text of one file or the events object written inline, as the common hook contract writes it. `namzu doctor` no longer warns about loop and `read` variables or names a shell keeps for itself.

The entries live while the plugin is on: enabling a plugin (`/plugins`, its saved state, `--plugin-dir`) attaches them and disabling it removes them at once. `/hooks` lists them apart from the plugin's JavaScript hooks with the plugin's name, event, command and matcher, `/plugins` shows how many a plugin ships, `namzu doctor` counts them and reports their problems, and `namzu plugin validate` checks every file and names each problem (`hook-entries-*`). `disableHooks` and `NAMZU_DISABLE_HOOKS` turn them off, and so does `hooksManagedOnly` (no plugin comes from the managed file); the plugin's JavaScript hooks are not touched by any switch. A project plugin is read only after the folder is trusted, and the terminal's trust prompt lists the entries a project's plugins would run, with the plugin's name, before the answer. The Desktop app's trust dialog does not read plugin folders yet.

A config-file hook that refers to a variable ending in `_PLUGIN_ROOT` or `_PLUGIN_DATA` still runs as it did (those names are given only to a plugin's own entries, so it sees them empty unless you set them with `env`); if it cannot find its program, the failure line and the `runtime.hooks` row of `namzu doctor` name the variable. Nothing has to be done to upgrade.
