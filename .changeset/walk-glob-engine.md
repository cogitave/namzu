'@namzu/sdk': patch

The sandbox file walk no longer depends on minimatch 9, which carries GHSA-g3hv-75wg-m249 (denial of service through globparts amplification, fixed only from minimatch 11.0.1). The walk compiles each pattern segment itself, so `glob`, `grep` and `Sandbox.walkFiles` return the same files as before for nearly every pattern; the differences found are: `[ab]/**` no longer lets a root file named `a b.md` through; `@(a|b)*` and `+(a)*` now match the name `a` (and `b`), which minimatch 9 missed; `!(a)*` no longer matches the name `a` and `!(.a)*` with hidden entries included no longer matches `.a`; and `?(a)*` or `*(a)*` no longer match a dot name such as `.env` unless hidden entries are included. An out-of-order range such as `[z-a]` matches nothing rather than failing. `@namzu/sdk` now declares `minimatch` ^11.0.1; nothing you call changes except one refusal. A repeated extglob group that can match the same text more than one way (`*(*(a))`, `*(a|aa)`, `+(a|aa)`, `+(*.ts)`, `+(a|)`, `*(?(a))`) is now refused with an error ("The pattern '...' repeats a group that can match the same text more than one way; use ** or {a,b} instead."), as a fix for catastrophic backtracking on a name that nearly matches; `glob` and `grep` return it as a tool error and `Sandbox.walkFiles` rejects with it. Write `{a,b}` or `**` instead, or a repeated group of plain names none of which starts another (`+(foo|bar)`, `*(ab|cd)`) or of one class (`+([a-z])`), which still work, as do `@( )`, `?( )` and `!( )`. A segment with more than three wildcards that can stretch (each `*`, `*( )` and `+( )`, consecutive `*` counted once) is also refused, with "The pattern '...' has more than three wildcards that can stretch; split it across folders or use fewer *.", because matching a long name against four or more of them takes seconds; `*foo*bar*` and `*.test.*` still work, and splitting the pattern across folders (`**/*a*/*b*`) avoids the limit.
