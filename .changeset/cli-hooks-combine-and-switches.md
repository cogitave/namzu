'@namzu/cli': major

Hooks from every config file now run together, and a hook can give the model context at the start of a session. This changes what an existing setup does, so it is a major.

**What now runs that did not before.** Until now the highest config file that had a `hooks` key replaced the whole key: a project's `namzu.config.json` with one hook switched off every hook in your `~/.namzu/config.yaml`, so a cloned repository, once trusted, quietly removed your own guard hooks; and a `hooks` key in the organisation-managed file discarded the rest. Now, for each event, the entries of the user file, the project file, the project's local file, the selected profile and the managed file are all attached, in that order (the managed file last, so its rewrite wins and its refusals still count). An entry that reads the same in two files runs once. Each attached entry remembers its file.

**What to do about it.** If a project's hooks used to hide yours and you did not notice, yours run now: look at `/hooks` (it lists every hook with the file it came from) or `namzu doctor` (`runtime.hooks`: hooks per file and whether a switch is on). To run without hooks from your files and the project's, set `disableHooks: true` in your own config file or start with `NAMZU_DISABLE_HOOKS=1`; the managed file's hooks and plugin hooks still run. An organisation can put `hooksManagedOnly: true` in the managed file so that only its own hooks attach; the key is ignored (with a note at launch) anywhere else. `disableHooks` in a project or local file is ignored (with a note at launch), so a repository cannot switch off your hooks; only your own file, the environment and the managed file can. Trust did not change: a project's hooks attach only once the folder is trusted.

**Session-start context.** A `session_start` hook's stdout (plain text on exit `0`) or `additionalContext` is now read: it becomes context for the model from the first turn and on every later turn, as the operator's hook speaking, fixed for the session and bounded to 8 000 characters. Until now that output was thrown away, so a hook that prints text at session start (a status line, a `git log`) now puts that text in front of the model. Silence it, or move the printing to stderr, if you do not want that. A resumed session runs the hook again (`source: "resume"`) and gets the new text; the earlier text is never kept, so it is never there twice. Hooks are also told `source` (`startup`, `resume`) on `session_start` and `reason` (`exit`, `replaced`) on `session_end`, and `matcher` on those events is tested against them.

Also: `/hooks` lists every attached hook with its file and the hooks plugins registered, and says in one line when a switch is on; the terminal's trust prompt names the hooks a folder's files declare (event and what they would run, at most eight) before you choose; a hook's `if` can name a file with a path glob (`Edit(src/**/*.ts)`, `Read(*.env)`), read as a `permissions` rule reads it; a hook gets `NAMZU_PROJECT_DIR`, the folder the session was started for; and a shell hook can redact a tool's result with `hookSpecificOutput.updatedToolOutput` on `post_tool_use` (the record marks that a hook replaced it). A hook's answer is read up to 64 KiB of stdout; a larger one is reported as ignored and the tool's original result stands.
