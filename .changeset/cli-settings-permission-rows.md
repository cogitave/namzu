'@namzu/cli': major
---

`namzu config get --json` now describes three more rows with new control kinds: `permissions` is `permission-rules`, `permissionChecks` is `permission-checks` and `browser.sites` is `sites` (all three were `json`); a script that read `control.kind` for these keys must handle the new kinds. `namzu config set permissions` now changes only the tool rules: `defaultMode`, `disableBypassMode`, `disableAutoMode`, `outsideRoot` and `autoMode` stay as written, a table that names one of them is refused (set them with their own keys), and clearing the key removes only the rules. The `allow`, `ask` and `deny` lists of `Tool(specifier)` strings are read, and saved back as the per-tool table. `namzu config get permissions` shows the rules without the mode keys. Each of the three now asks first only when a change lets more run without a person, and names it: a rule that allows added or made more permissive, a deny or ask rule removed; a check removed or changed; a site that becomes `act` or stops being `deny`. A change that only restricts saves at once. Each entry is refused with the loader's own words, and a site is written the way the loader reads it. The `permissionChecks` and `browser.sites` examples now show a valid value: the old check example gave `input` as a string and the old site example had no scheme, and the loader refuses both. To keep the old behaviour of a script that wrote the whole permissions table, set each mode key with its own key (`permissions.defaultMode`, `permissions.disableBypassMode`, `permissions.disableAutoMode`, `permissions.outsideRoot`, `permissions.autoMode`) and send only the rules to `permissions`; `config unset permissions` no longer clears the mode keys, so unset each one by its own key. A tool in a rule or a check must now be written as the engine names it, in lower case (`bash`, not `Bash`), because the other spelling was saved and never matched.
