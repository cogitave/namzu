---
'@namzu/sdk': major
---

Hooks gain a few things an operator and an embedder asked for, and a hook's `matcher` now reads tool names the way `if` does. The matching change makes an existing configuration behave differently (it is why this is a major); the rest adds. A host with its own switch over `PluginHookResultFor<'session_start'>` or the `replace` verdict needs to allow the new members.

- A `session_start` hook can give the model context for the whole session. A shell hook's plain stdout on exit `0` or `hookSpecificOutput.additionalContext`, and an in-process hook's `continue` with `context` or `annotate`, are read by the new `sessionStartHookContext(results)` (joined in answer order, bounded to `MAX_HOOK_CONTEXT_CHARS`, 8 000, with `[truncated]` marking a cut). `frameOperatorHookContext(texts)` is the frame `user_prompt_submit` context already carried (`Context from the operator's hooks:`), now one function; `boundHookContext` and `boundHookReplacement` are exported with their limits. The SDK does not deliver the text itself: a host calls `sessionStartHookContext` on the results of `executeHooks('session_start', ...)` and gives it to its turns. `PluginHookResultFor<'session_start'>` is now `continue | annotate` (was `continue`).
- Session hooks are told why. `PluginHookContext.source` (`startup` or `resume`, type `PluginSessionSource`) on `session_start` and `PluginHookContext.endReason` (`exit` or `replaced`, `PluginSessionEndReason`) on `session_end`. A shell hook reads them as `source` and `reason` on stdin, and `matcher` on these two events is tested against them, so `matcher: "resume"` runs a hook only on a resumed session.
- A shell hook can replace a tool's result. `hookSpecificOutput.updatedToolOutput` on `post_tool_use` carries the text the model should read instead (cut to `MAX_HOOK_REPLACEMENT_CHARS`, 32 000). The replacement is marked beside the result, in what the model reads and in the recorded result, with a `[Hook note]` saying a hook replaced it. The `replace` verdict gains `disclose` (opt in to the same mark for an in-process hook; off by default, so a plugin that redacts quietly is unchanged), and it can carry `context`, `halt` and `notice` like `continue`.
- A hook's `if` can name a file tool with a path glob (`Edit(src/**/*.ts)`, `Read(*.env)`). The host supplies the path reading as `pathFilter` in the options of `attachShellHooks` (`ShellHookPathFilter`), so the CLI reads it exactly as it reads a `permissions` path rule. Without a `pathFilter` a path pattern still runs the hook, as before. `shellHookIfMatches` takes it as a fourth argument.
- A shell hook's environment has `NAMZU_PROJECT_DIR`, the folder the session was started for (the `projectDir` option of `attachShellHooks`; without it, `cwd`). `NAMZU_PROVIDER` and `NAMZU_MODEL` are inherited from the launching environment and `NAMZU_SHELL_TAG` is an internal tag; neither is part of the contract and the hooks page now says so.
- `ShellHookEntry` and the other entry types take an optional `source` (where the entry was declared); it has no effect on how the hook runs. `PluginLifecycleManager.listHooks()` lists the hooks attached right now by plugin id and event, for a host that shows them.
- `subagent_start` was written twice in the `PluginHookEvent` union with contradicting comments; the duplicate is gone. The type did not change.
- A redaction hook can fail closed. On a `post_tool_use` or `post_tool_use_failure` shell hook, `onFailure: block` now withholds the tool's result when the hook fails (could not start, timed out, exited with a code other than `0` or `2`, or printed an answer that does not read): the model reads one line saying a hook guarding the result failed and the result is not shown, with the short reason, and the record carries the replaced-result mark. The call has already run; this does not undo it. Nothing changes without `onFailure: block`: the failure is logged and the original result is shown, so a hook used for redaction should set it. An answer over the 64 KiB read limit is now reported as too large, with the limit, instead of as unreadable JSON (`ShellHookOutcome` gains an optional `stdoutTruncated`). In-process hooks are unchanged.

- **`matcher` names a tool as `if` does (a changed matching rule).** `shellHookMatches(matcher, name, { tool })` compared names exactly and case-sensitively, so `matcher: "Bash"` never matched the tool `bash` and a guard written that way silently never ran. Now, on a tool event and `permission_request` (the `tool: true` option; `createShellHook` sets it), a listed name or prefix is compared without regard to case and through the names skills write (`SKILL_TOOL_NAME_ALIASES`: `Bash`, `Read`, `Edit`, `MultiEdit` for `edit`, `Web*` for `web_fetch`, and so on); a regular expression is still tested against the tool's own name and is also tested against the names skills write for that tool, so `Bash.*` and `^(Edit|Write)$` fire; a list part ending in `.*` is also tried as a regular expression. On the other events (a notification's type, an agent's name, `source`, `reason`) names compare without regard to case and no tool alias applies. Nothing matches less than before, but a guard that never ran now runs, and with no options `shellHookMatches` itself is now case-insensitive. **What to do:** a hook that must not fire for the capitalised spelling of a tool says so with an `if` or a regular expression; otherwise nothing to change. A script that tests `tool_name` against `"Bash"` is unaffected: `tool_name` is still `bash`.
- A host can give an event a shorter default deadline and hear of a timeout. `ShellHookOptions.defaultTimeoutMs` (an object keyed by event) applies to entries that set no `timeoutMs`; an entry's own is honoured as written; `ShellHookOptions.onTimeout({ event, hook, timeoutMs })` is called when a hook ran out its deadline and was ended. Both are optional and change nothing when absent.
- The hooks page states what a script moved from another host must expect: the field names are common, the values are Namzu's own (lower-case tool names, `path` as a file tool's key, `tool_response` an object, no `tool_use_id` on a single-call event). `updatedMCPToolOutput` is ignored, and an `updatedToolOutput` that is not a string makes the whole answer unreadable, so what happens next follows `onFailure`.
