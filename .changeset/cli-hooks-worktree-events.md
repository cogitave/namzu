A hooks block can now name `worktree_create` (`WorktreeCreate`) and `worktree_remove` (`WorktreeRemove`). A `worktree_create` hook makes the worktree itself (another version-control tool, a prepared checkout, a plain copy) and prints its folder as the last line; Namzu uses it for a sub-agent's `workspace: "worktree"`, `namzu worktree create`, `namzu worktree fork` and `/worktree create`, including outside a Git checkout, and creates none itself. If the hook fails or prints no path, the creation fails with a line naming the hook and what it printed; it never falls back to Git. A `worktree_remove` hook does the removing. A worktree a hook made is not listed by `namzu worktree list`, is kept when a sub-agent changed it and, with no remove hook, is left in place with a line saying where. `/hooks` says that a matcher, `if` or `once` on these two events is ignored. Nothing changes for configs that use neither. The page on managed worktrees is corrected: a delegated child's checkout that ends with no changes is removed automatically; one made by `namzu worktree create` never is. `namzu worktree create` and `fork` in a folder nobody trusted refuse, with exit 64 and nothing created, when the folder's own config declares a `worktree_create` hook (it would not run there, and Git would make the worktree it was written to replace): trust the folder first by running `namzu` in it once. `namzu doctor` says when a `file_changed` hook names no file.

A `worktree_create` or `worktree_remove` hook shipped by a plugin takes over like one in a config file; one in a skill or an agent file is set aside with a note. A delegated child that works in a worktree a hook made still gets its agent file's hooks, and they end when it ends.
