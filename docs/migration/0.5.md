# Migrating to `@namzu/sdk@0.5.0`

`0.5.0` is a minor release under pre-1.0 semver that is explicitly allowed to
break. It closes a set of prompt-injection and fail-open surfaces in the plugin,
probe, and tool-naming layers, and it adds a reliability layer around provider
calls.

Most of the release is additive — the reliability work (typed provider errors,
bounded retries, context-overflow recovery, cancellation) requires no code
changes and is documented in [Reliability and Cancellation](../sdk/runtime/reliability.md).

This page is the contract for the parts that are **not** additive. There are
three behavior changes a consumer can notice, and one of them can make
previously-working tool calls start failing.

## Section A — The plugin namespace separator is `__`

The separator between a plugin name and its components was `:`. It is now `__`,
and **the old form is not resolved**. A `:` name is simply an unknown tool.

Before (`0.4.x`):

```
docs-tools:summarize_workspace
fs-plugin:mcp__fs__read_file
```

After (`0.5.0`):

```
docs-tools__summarize_workspace
fs-plugin__fs__read_file
```

Two reasons, and the second is why there is no compatibility shim:

1. **Strict providers reject `:` in a function name.** The composed name is the
   name the model sees and calls, so it has to be a name a provider will accept:
   `[a-zA-Z0-9_-]`, at most 64 characters.
2. **Resolving both spellings was a privilege-escalation hole.** Probe vetoes,
   plugin `pre_tool_use` hooks, and the verification gate all match on the raw
   name the model supplied, while only the registry resolved aliases. A tool
   denied as `github__delete_repo` was still reachable as `github:delete_repo`.
   There is now exactly one canonical name at every layer.

An unknown name containing `:` gets an extra hint line in the error returned to
the model, pointing at the new separator. That is a diagnostic aid only — the
name is **not** resolved.

### What you have to do

| If you... | Then... |
| --- | --- |
| Hardcode plugin tool names in allowlists, `allowedTools`, or verification rules | Rewrite them with `__` |
| Match plugin tool names in probe `where` filters or hook handlers | Rewrite them with `__` |
| Have persisted run histories or plugin manifests holding `:` names | **Re-create them.** A `:` name in a stored history no longer resolves |
| Compose names by hand (`` `${plugin}:${tool}` ``) | Use `PluginResolver.namespaceName()` or `composeToolName()`, which validate |

### The component contract

Each component of a composed name (the plugin name, an MCP server alias, a leaf
tool name) must match `^[a-zA-Z0-9_-]+$` and **may not contain `__`**.

Single underscores stay legal — `read_file` is a fine tool name. Only the
doubled form is reserved, and that exclusion is what makes composition
injective: `(fs, read_file)` gives `fs__read_file`, `(fs_read, file)` gives
`fs_read__file`, and neither can be confused for the other when split apart.

Composed names are validated and length-checked **before** the enable
transaction begins registering anything, so a plugin cannot half-register and
then fail. A plugin that fails to enable is left in `error` status, not silently
back in `installed` — the manifest is broken and re-enabling will fail the same
way until it is fixed.

## Section B — Veto handlers fail closed

**A veto handler that throws now DENIES.** Previously the throw was logged and
the operation proceeded.

```ts
probe.veto('tool_executing', (event) => {
  // If this throws on an unexpected event shape...
  return event.input.command.startsWith('rm') ? 'deny' : 'allow'
})
```

In `0.4.x` a crash here waved the tool call through. In `0.5.0` it denies. The
`where` predicate is evaluated inside the same boundary, so a filter that
crashes on an unexpected input shape denies too rather than escaping and
aborting the run.

A veto is an authorization decision, and an authorizer that cannot answer must
not be read as an allow.

### What you have to do

Audit any veto handler whose body or `where` filter could throw on an input
shape it did not anticipate — a `tool_executing` event for a tool whose `input`
has no `command` field is the common case. A handler that was quietly crashing
in `0.4.x` was not enforcing anything; in `0.5.0` it starts denying.

If a veto is genuinely non-critical, opt out per handler:

```ts
probe.veto('tool_executing', handler, { onError: 'allow' })
```

A deny that came from a throwing handler carries `reason: PROBE_ERROR_REASON`
(exported), so you can distinguish it from a deliberate deny.

## Section C — An unknown tool name returns an error to the model

**A tool name the registry does not hold now comes back as a tool-level error
result instead of throwing.**

In `0.4.x` a mistyped or hallucinated name rejected out of the executor's tool
batch and aborted the whole run. In `0.5.0` it returns an error result the model
can read and correct, and the other tool calls in the same batch still execute.

This is a behavior change rather than a break: nothing you wrote stops
compiling. But if you relied on an unknown tool name surfacing as a thrown error
in your run wrapper, it no longer does — it surfaces as a failed tool result in
the event stream.

## Section D — Third-party tool names are canonicalized, not rejected

Names **you** author stay strictly validated, because you can fix them: the
plugin name, its own tools, its MCP server aliases.

Names a **third party** authors are now canonicalized instead, because you
cannot fix them: an MCP server's own tool names and connector method names. You
cannot rename a tool that lives inside someone else's server.

```ts
import { canonicalizeToolName } from '@namzu/sdk'

canonicalizeToolName('notion.search')  // 'notion_search'
canonicalizeToolName('db:query')       // 'db_query'
```

The mapping is deterministic and stable across restarts (an over-long name gets
a truncated prefix plus a fixed hash suffix), so a canonicalized name persisted
in a run history still resolves after a restart. `__` collapses to `_`, so a
canonicalized name can never be mistaken for a composed one.

**The remote is still invoked under its original name.** The adapters capture it
in the tool's `execute` closure; renaming the registry key is invisible to the
server on the other end.

In `0.4.x` a single nonconforming remote tool name failed the registration and
aborted the entire plugin enable. Now it is repaired — or, if plugin + server +
tool cannot compose within the 64-character provider limit, skipped with a
`plugin_tool_skipped` lifecycle event while the rest of the plugin enables.

## Section E — Plugin MCP `env` supports interpolation (additive)

`env` values in a plugin manifest's `mcpServers` entries now expand `${VAR}` and
`${env:VAR}` against the process environment:

```json
{
  "mcpServers": [
    {
      "name": "github",
      "command": "node",
      "args": ["./mcp/github-server.js"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}",
        "LITERAL": "$${NOT_A_VAR}"
      }
    }
  ]
}
```

- `$${VAR}` is an escape yielding the literal text `${VAR}`.
- A reference to a variable that is **not set** throws at `enable()` rather than
  expanding to an empty string. A blank API key should stop the enable, not
  surface later as an opaque auth failure from the MCP server.
- **`command` and `args` are not interpolated** — the stdio transport logs them
  verbatim at connect time, and a credential does not belong in a log line.
- `EnvInterpolationError` never embeds the offending value. MCP `env` is exactly
  where credentials live, and the message is persisted on the plugin registry
  record, emitted on `plugin_error`, and written to the error log. The env key
  names the manifest line, which is all anyone needs to fix it.

This is additive: a manifest with no `${...}` syntax behaves exactly as before.

## Section F — Plugin hooks gain an `onError` policy (additive)

`PluginHookDefinition` gains an optional `onError: 'continue' | 'error'`,
defaulting to `'error'` — the existing fail-closed behavior, where a throwing or
timing-out hook blocks the operation it guards.

An observer-style hook that must never block a run can opt into `'continue'`:

```ts
export const hooks = [
  {
    event: 'post_tool_use',
    onError: 'continue',
    async handler(context) {
      await sendToAnalytics(context)   // a crash here must not fail the run
      return { action: 'continue' }
    },
  },
]
```

A continued error stays **visible**: the `plugin_hook_completed` run event gains
an `error` field, set whenever the handler threw, even when the policy converted
the throw into a `continue`. A crashed hook must not be indistinguishable from a
clean one.

The default is unchanged, so existing hooks keep their current semantics.

## What did NOT change

- `defineTool()` signature and semantics.
- Provider-registration APIs (`registerOpenAI`, `registerAnthropic`, etc.).
- Run, iteration, and tool event shapes, apart from the new optional `error`
  field on `plugin_hook_completed` and the new `plugin_tool_skipped` lifecycle
  event.
- Session hierarchy types.
- Non-plugin tool names. A tool you register directly is unaffected by the
  separator change — only *composed* plugin names use `__`.
- Frame content. Sub-agent and advisory payloads now reach the model **verbatim**
  (see below), which is a fidelity improvement, not a break.

## Frames are authenticated rather than escaped

Not a migration item — no consumer API changed — but worth understanding because
it changes what the model sees.

Sub-agent results and advisory blocks are wrapped in
`<task-notification-{nonce}>` / `<advisory-result-{nonce}>` tags carrying a
per-run nonce, and the system prompt states that only nonce-bearing tags are
framework-authored. A sub-agent that emits a closing tag can no longer forge a
frame boundary.

Because the boundary is now the thing an attacker cannot reproduce, the payload
inside a frame is passed through **verbatim** — code, paths, and ampersands
reach the model byte-exact instead of HTML-escaped. Tool names and descriptions
in the prompt catalogue are still escaped: they are metadata, not content the
model has to reproduce.

## What's new and additive

The reliability layer needs no migration. See
[Reliability and Cancellation](../sdk/runtime/reliability.md) for:

- `ProviderRequestError` and the typed error taxonomy across all seven providers
- `RetryConfig` — bounded retries with jittered backoff, honoring `Retry-After`
- Reactive context-overflow recovery
- `finishReason: 'length'` handling
- `ChatCompletionParams.signal` and `ProviderCapabilities.supportsAbortSignal`
- `repairDanglingMessages()` / `prepareResumeMessages()`
