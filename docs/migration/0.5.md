# Migrating to `@namzu/sdk@0.5.0`

`0.5.0` is a minor release under pre-1.0 semver that is explicitly allowed to
break. It closes a set of prompt-injection and fail-open surfaces in the plugin,
probe, and tool-naming layers, adds a reliability layer around provider calls,
gives a run one canonical id, and makes a run that pauses for a human survive the
process it paused in.

This page is the contract for the parts that are **not** additive. Some are
API-shaped and can make previously-working tool calls or type-checks start
failing; others are behavioral and change what a run costs, what it is persisted
as, and which events it emits.

The reliability work (typed provider errors, bounded retries, context-overflow
recovery, cancellation) needs no code changes to compile against — but it is
**not** invisible at runtime, because retry is on by default. Read
[Section G](#section-g--retry-is-on-by-default) before you assume it is.
Everything else about the layer is documented in
[Reliability and Cancellation](../sdk/runtime/reliability.md).

## Section A — The plugin namespace separator is `__`

The separator between a plugin name and its components was `:`. It is now `__`,
and **the old form is not resolved**. A `:` name is simply an unknown tool.

Before (`0.4.x`):

```
docs-tools:summarize_workspace
fs-plugin:mcp__fs__read_file
```

After (`0.5.0`):

```
docs-tools__summarize_workspace
fs-plugin__fs__read_file
```

Two reasons, and the second is why there is no compatibility shim:

1. **Strict providers reject `:` in a function name.** The composed name is the
   name the model sees and calls, so it has to be a name a provider will accept:
   `[a-zA-Z0-9_-]`, at most 64 characters.
2. **Resolving both spellings was a privilege-escalation hole.** Probe vetoes,
   plugin `pre_tool_use` hooks, and the verification gate all match on the raw
   name the model supplied, while only the registry resolved aliases. A tool
   denied as `github__delete_repo` was still reachable as `github:delete_repo`.
   There is now exactly one canonical name at every layer.

An unknown name containing `:` gets an extra hint line in the error returned to
the model, pointing at the new separator. That is a diagnostic aid only — the
name is **not** resolved.

### What you have to do

| If you... | Then... |
| --- | --- |
| Hardcode plugin tool names in allowlists, `allowedTools`, or verification rules | Rewrite them with `__` |
| Match plugin tool names in probe `where` filters or hook handlers | Rewrite them with `__` |
| Have persisted run histories or plugin manifests holding `:` names | **Re-create them.** A `:` name in a stored history no longer resolves |
| Compose names by hand (`` `${plugin}:${tool}` ``) | Use `PluginResolver.namespaceName()` or `composeToolName()`, which validate |

### The component contract

Each component of a composed name (the plugin name, an MCP server alias, a leaf
tool name) must match `^[a-zA-Z0-9_-]+$` and **may not contain `__`**.

Single underscores stay legal — `read_file` is a fine tool name. Only the
doubled form is reserved, and that exclusion is what makes composition
injective: `(fs, read_file)` gives `fs__read_file`, `(fs_read, file)` gives
`fs_read__file`, and neither can be confused for the other when split apart.

Composed names are validated and length-checked **before** the enable
transaction begins registering anything, so a plugin cannot half-register and
then fail. A plugin that fails to enable is left in `error` status, not silently
back in `installed` — the manifest is broken and re-enabling will fail the same
way until it is fixed.

## Section B — Veto handlers fail closed

**A veto handler that throws now DENIES.** Previously the throw was logged and
the operation proceeded.

```ts
probe.veto('tool_executing', (event) => {
  // If this throws on an unexpected event shape...
  return event.input.command.startsWith('rm') ? 'deny' : 'allow'
})
```

In `0.4.x` a crash here waved the tool call through. In `0.5.0` it denies. The
`where` predicate is evaluated inside the same boundary, so a filter that
crashes on an unexpected input shape denies too rather than escaping and
aborting the run.

A veto is an authorization decision, and an authorizer that cannot answer must
not be read as an allow.

### What you have to do

Audit any veto handler whose body or `where` filter could throw on an input
shape it did not anticipate — a `tool_executing` event for a tool whose `input`
has no `command` field is the common case. A handler that was quietly crashing
in `0.4.x` was not enforcing anything; in `0.5.0` it starts denying.

If a veto is genuinely non-critical, opt out per handler:

```ts
probe.veto('tool_executing', handler, { onError: 'allow' })
```

A deny that came from a throwing handler carries `reason: PROBE_ERROR_REASON`
(exported), so you can distinguish it from a deliberate deny.

## Section C — An unknown tool name returns an error to the model

**A tool name the registry does not hold now comes back as a tool-level error
result instead of throwing.**

In `0.4.x` a mistyped or hallucinated name rejected out of the executor's tool
batch and aborted the whole run. In `0.5.0` it returns an error result the model
can read and correct, and the other tool calls in the same batch still execute.

This is a behavior change rather than a break: nothing you wrote stops
compiling. But if you relied on an unknown tool name surfacing as a thrown error
in your run wrapper, it no longer does — it surfaces as a failed tool result in
the event stream.

## Section D — Third-party tool names are canonicalized, not rejected

Names **you** author stay strictly validated, because you can fix them: the
plugin name, its own tools, its MCP server aliases.

Names a **third party** authors are now canonicalized instead, because you
cannot fix them: an MCP server's own tool names and connector method names. You
cannot rename a tool that lives inside someone else's server.

```ts
import { canonicalizeToolName } from '@namzu/sdk'

canonicalizeToolName('notion.search')  // 'notion_search_1gn6nda'
canonicalizeToolName('db:query')       // 'db_query_0fa0aax'
canonicalizeToolName('read_file')      // 'read_file'  — already valid, untouched
```

**Any repair appends a hash of the original name.** Sanitizing alone is lossy:
`a.b`, `a/b`, `a__b` and `a_b` all sanitize to `a_b`, so two different remote
tools would claim one registry key and whichever server was enumerated first
would win. MCP enumeration order is not stable across restarts, which means a
canonical name persisted in a run history could come back bound to a *different*
remote tool. So a name that needs any repair at all — a substituted character, a
collapsed `__`, a truncation — comes back as `<base>_<hash7>`, where the hash is
taken over the original string. A name that needs no repair is returned unchanged
and stays readable.

**A repaired name is itself a legal name**, which is the one subtlety worth
knowing: without care, a server advertising the literal tool name `a_b_04la3gs`
would pass through untouched and land exactly on top of the repaired form of
`a.b`. So the suffix *shape* — `_` followed by seven base36 digits opening with
`0` or `1` — is reserved. A raw name wearing it is repaired too, even if it is
otherwise perfectly valid. The shape is narrow enough that ordinary names are
unaffected: `send_message`, `get_weather` and `run_command` all pass through
untouched.

The mapping is a pure function of the raw name: identical in every process and
every release, and independent of registration order, so a canonicalized name
persisted in a run history still resolves after a restart. `__` never survives, so
a canonicalized name can never be mistaken for a composed one. The 32-bit hash
makes an aliasing collision astronomically unlikely rather than impossible, and it
is not the last line of defence: a canonical name that is already taken is skipped
with a `plugin_tool_skipped` event, never silently aliased onto the tool that got
there first.

**A plugin's MCP leaf is canonicalized against what its namespace leaves it** —
64 characters minus `plugin__server__` — so a long remote name is shortened to fit
rather than dropped. A tool is skipped only when that budget cannot hold even a
minimal repaired name, or when the server advertised the same raw name twice.

**The remote is still invoked under its original name.** The adapters capture it
in the tool's `execute` closure; renaming the registry key is invisible to the
server on the other end.

In `0.4.x` a single nonconforming remote tool name failed the registration and
aborted the entire plugin enable. Now it is repaired — or, if plugin + server +
tool cannot compose within the 64-character provider limit, skipped with a
`plugin_tool_skipped` lifecycle event while the rest of the plugin enables.

## Section E — Plugin MCP `env` supports interpolation (additive)

`env` values in a plugin manifest's `mcpServers` entries now expand `${VAR}` and
`${env:VAR}` against the process environment:

```json
{
  "mcpServers": [
    {
      "name": "github",
      "command": "node",
      "args": ["./mcp/github-server.js"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}",
        "LITERAL": "$${NOT_A_VAR}"
      }
    }
  ]
}
```

- `$${VAR}` is an escape yielding the literal text `${VAR}`.
- A reference to a variable that is **not set** throws at `enable()` rather than
  expanding to an empty string. A blank API key should stop the enable, not
  surface later as an opaque auth failure from the MCP server.
- **`command` and `args` are not interpolated** — the stdio transport logs them
  verbatim at connect time, and a credential does not belong in a log line.
- `EnvInterpolationError` never embeds the offending value. MCP `env` is exactly
  where credentials live, and the message is persisted on the plugin registry
  record, emitted on `plugin_error`, and written to the error log. The env key
  names the manifest line, which is all anyone needs to fix it.

This is additive: a manifest with no `${...}` syntax behaves exactly as before.

## Section F — Plugin hooks gain an `onError` policy (additive)

`PluginHookDefinition` gains an optional `onError: 'continue' | 'error'`,
defaulting to `'error'` — the existing fail-closed behavior, where a throwing or
timing-out hook blocks the operation it guards.

An observer-style hook that must never block a run can opt into `'continue'`:

```ts
export const hooks = [
  {
    event: 'post_tool_use',
    onError: 'continue',
    async handler(context) {
      await sendToAnalytics(context)   // a crash here must not fail the run
      return { action: 'continue' }
    },
  },
]
```

A continued error stays **visible**: the `plugin_hook_completed` run event gains
an `error` field, set whenever the handler threw, even when the policy converted
the throw into a `continue`. A crashed hook must not be indistinguishable from a
clean one.

The default is unchanged, so existing hooks keep their current semantics.

## Section G — Retry is on by default

No API changed here, and nothing you wrote stops compiling. But a run that used to
issue exactly one request per model call can now issue up to **three**, and that
is not something to discover from a bill.

`RetryConfig` defaults to:

| Field | Default | Effect |
|---|---|---|
| `enabled` | `true` | Retries are on unless you turn them off. |
| `maxAttempts` | `3` | Up to 3 physical requests per logical model call. |
| `baseDelayMs` | `1000` | Full-jitter exponential backoff base. |
| `maxDelayMs` | `30000` | Ceiling on any single wait, including a server-advised `Retry-After`. |
| `overflowAttempts` | `2` | Context-overflow reductions + reissues per iteration. |

Only `throttle`, `server` and `network` errors are retried. An `auth` or
`bad_request` failure still fails on the first attempt — a retry could not help
it. What changes for you:

- **Request count and cost.** A transient 429 or 503 that used to surface as a
  failed run is now absorbed, at the price of up to 3x the requests for the calls
  that hit one.
- **Latency and failure timing.** A failing call now takes as long as its backoff
  schedule allows before it gives up, bounded by the run's `timeoutMs`.
- **Provider-side retries are gone.** Every adapter now pins its vendor SDK to a
  single physical attempt, so the SDK's cap is the real bound. Before, an
  application-level retry would have multiplied against a vendor default of 2-3.

To restore 0.4.x behavior exactly, disable it per run:

```ts
await agent.run(prompt, {
  retry: { enabled: false, maxAttempts: 1, baseDelayMs: 0, maxDelayMs: 0, overflowAttempts: 0 },
})
```

Or tune it rather than remove it:

```ts
await agent.run(prompt, {
  retry: { enabled: true, maxAttempts: 2, baseDelayMs: 500, maxDelayMs: 5_000, overflowAttempts: 1 },
})
```

**One caveat worth knowing.** `runConfig.retry` governs the main iteration loop.
The SDK's ancillary model calls — the compaction verifier, the task router, the
advisory consult — carry their own bounded retry budget and their own wall clock,
and do **not** read `runConfig.retry`. Disabling retry on a run therefore does not
disable it everywhere inside that run. They are bounded, but they are not yours to
configure yet.

## Section H — One canonical run id

A run had two names. The API minted a run id and passed it to the agent's config
builder; the builders dropped it; the agent minted another one for the actual
run. The SSE mapper hid the split by overwriting `event.runId` with an id passed
to it separately, so every client saw a consistent id and no one could see that
the run record on disk was named something else.

Now a run has exactly one id, minted once, used everywhere.

### `BaseAgentConfig.runId` (additive)

Supply a run id and it **is** the run id — on the run record, on every
`RunEvent`, and in the run's on-disk directory name. Omit it and the agent mints
exactly one.

```ts
await agent.run(input, { ...config, runId: myRunId })
// the run record, every event, and .namzu/…/runs/<myRunId>/ all agree
```

### `mapRunToStreamEvent` loses its second argument (breaking)

```ts
// 0.4.x — the second argument was stamped onto every event, replacing event.runId
const mapped = mapRunToStreamEvent(event, runId)

// 0.5.0 — run_id comes off the event
const mapped = mapRunToStreamEvent(event)
```

Drop the argument. There is nothing to replace it with: the substitution existed
only because the two ids disagreed, and it could only ever mask that. The same
applies to the deprecated alias `mapSessionToStreamEvent`.

### `AbstractAgent.createRunId()` → `resolveRunId(config)` (breaking for subclasses)

If you subclass `AbstractAgent`, take the run id from the base and thread it into
`query()`. An agent that mints its own id silently renames its caller's run.

```ts
// 0.4.x
const runId = this.createRunId()

// 0.5.0 — the caller's id if there is one, otherwise a fresh one
const runId = this.resolveRunId(config)
```

### A sub-agent's events now carry the child's run id (behavioural)

A spawned child is its own run: its own record, its own directory, its own
budget, linked to its parent by `parentRunId`. Its events reach the parent's
listener — and they used to be **relabelled** as the parent's on the way to the
wire. They are not anymore. They carry the child's `run_id`, plus `lineage`
(`parentSessionId`, `rootSessionId`, `depth`) to place them.

If your client assumes every event on a run's stream carries that run's id, read
`lineage` instead of assuming. Task lifecycle events —
`agent.pending` / `agent.completed` / `agent.failed` / `agent.canceled` — are
unchanged: they are the *parent's* events about its child, and they keep the
parent's id.

A `RouterAgent`'s delegate is the exception that proves the rule: a route is a
tail call, not a spawn, so the delegate runs under the router's id. There is one
run there, not two.

## Section I — A paused run is a state, not a completion

In `0.4.x` a run that stopped for a human had no state to stop in.
`RunPersistence` knew only running / completed / failed / cancelled, `pause` set
a `stopReason` and nothing else, and the run was then marked **completed** and
emitted `run_completed`. A run waiting on a decision was persisted as finished.

`0.5.0` makes the suspension a real, non-terminal state, and makes the pause
**durable**: the question is persisted, the process is freed, and the run is
resumed later from its checkpoint. The full contract is
[Durable Pause](../sdk/runtime/durable-pause.md). This section is only what
breaks.

### `WireRunStatus` gains `awaiting_input` (breaking for exhaustive consumers)

```ts
type WireRunStatus =
  | 'queued' | 'running'
  | 'awaiting_input'      // ← new
  | 'completed' | 'failed' | 'cancelled' | 'cancelling' | 'expired'
```

A `switch` over `WireRunStatus` with no `default` stops compiling until it
handles the new member. It maps to A2A `input-required` (`RUN_STATUS_TO_A2A`),
which has always meant exactly this.

Previously a run waiting on a human was reported as `running`, on the theory
that a pause was an internal detail. It is not: a client that cannot see the
difference cannot know it is the one being waited on, or that the run will sit
there until it answers.

### `query({ resumeFromCheckpoint })` throws where it used to fail the run

Two changes, and the first is why the second matters.

```ts
// 0.4.x — a refused resume came back as a Run with status 'failed'
const run = await drainQuery({ resumeFromCheckpoint: cp, runId })

// 0.5.0 — a refused resume THROWS, and writes nothing
try {
  const run = await drainQuery({ resumeFromCheckpoint: cp, runId })
} catch (err) {
  if (err instanceof RunNotResumableError) { /* err.status: 'completed' | 'failed' | 'cancelled' */ }
}
```

1. **It throws `RunNotResumableError`** instead of returning a failed `Run`. The
   old path routed the refusal through the run's error handler, which marked the
   run `failed` and persisted that — so *attempting* to resume a cancelled run
   overwrote its record and emptied its `messages.json`. A refusal now happens
   before the first write and leaves the run byte-identical.
2. **It refuses every terminal status**, not only `cancelled`. A `completed` or
   `failed` run used to be re-driven happily **under its own id**, overwriting
   its record with the second drive's.

Re-driving a finished run from a checkpoint is still a legitimate thing to want.
It is a **fork**, it mints a new run id, and it has its own entry point:
`prepareForkState()`. See [Replay](../sdk/runtime/replay.md).

Crash recovery is unaffected: a non-terminal run (`idle`, `running`, or an
`awaiting_input` run whose decision is already settled) still resumes.

### A second concurrent segment throws `RunLeaseHeldError`

One run is driven by **one segment at a time**. A segment that cannot take the
run's lease does not run:

```ts
import { RunLeaseHeldError } from '@namzu/sdk'
// err.holderId, err.token, err.renewedAt, err.expiresAt
```

Before, two processes could drive the same run concurrently, both write
`run.json` and `messages.json`, and the last writer won — discarding the other's
work, including tools it had already executed. There was no error; there was
silent divergence.

The lease is not optional and cannot be switched off. `QueryParams.lease` tunes
its TTL (30s), heartbeat (10s) and holder id. Details, including the fencing
token and the three states an operator can observe, are in
[Durable Pause §5](../sdk/runtime/durable-pause.md#5-the-run-lease-who-is-driving-this-run).

### Runs write a `leases/` directory

A run's directory gains `leases/` (the lease sequence, whose file numbers are the
fencing tokens) and `decisions/` (the durable single-use claims). Anything that
enumerates a run directory and assumes it knows every entry needs to tolerate
them.

### `AgentManagerContract.cancel` / `cancelAll` are async (breaking for implementers)

```ts
// 0.4.x
cancel(taskId: TaskId): void
cancelAll(parentRunId: RunId): void

// 0.5.0
cancel(taskId: TaskId): Promise<void>
cancelAll(parentRunId: RunId): Promise<void>
```

A cancel now has to **reach the disk**. A child parked on a durable decision has
no live process to signal — its generator returned when it parked — so a cancel
that only aborts a signal leaves the decision `pending` and the run
`awaiting_input`, and a leaked resume token can still run its tools. If you
implement `AgentManagerContract`, return a promise and let callers await it.

`RunPersistence.markSuspended` is async for the same reason: `awaiting_input`
used to reach `run.json` only at the very end of the generator, so a process
killed mid-pause left a run stuck at `idle` holding a live decision.

**`PersistedRunMeta` gains `awaitingDecision`** (a pointer to the checkpoint and
request the run is parked on) and `replayOf` (fork provenance).

### `tool_review_completed` is no longer emitted on a pause (wire behavior)

A pause has no outcome — the question is still open. The pause path used to emit
`tool_review_completed { decision: 'rejected' }` on its way out, so a client that
closed its approval dialog on that event told its user the tools were **denied**
while the batch sat on disk waiting to be approved. Once the pause became
durable it also became self-contradicting: hours later the human approves and a
*second* `tool_review_completed` goes out for the same `requestId` saying
`approved`.

**A pause is announced by `run_paused`.** If your client closed its review UI on
`tool_review_completed`, switch it to `run_paused` for the pause case.
`tool_review_completed` now fires exactly once, when the review is actually
decided.

Two additive event changes ride along: `tool_review_requested` gains `requestId`
and `checkpointId` (which is how an out-of-process answer addresses it), and a
new `tool_execution_uncertain` event reports a call that was dispatched, lost its
result to a crash, and was deliberately **not** re-executed.

### The plan gate now ends the run instead of parking it (behavior)

A `plan_approval` cannot park durably: the checkpoint captures no `PlanManager`,
so a resumed run rebuilds an empty one and never re-fires the gate — an
`approve_plan` answered tomorrow would be recorded against a plan that no longer
exists. With no in-process reviewer, the plan gate **rejects and the run ends**,
which is an honest refusal rather than a pause that cannot be come back to.

If you rely on plan approval, pass a `resumeHandler` that answers it in-process.

### `timeoutMs` measures active execution time (behavior)

| Limit | 0.5.0 semantics across a resume |
| --- | --- |
| `tokenBudget` | **Lifetime.** Accumulated across every segment |
| `costLimitUsd` | **Lifetime.** Accumulated across every segment |
| `maxIterations` | **Lifetime.** Carried, not reset |
| `timeoutMs` | **Active execution time** — time the run spends *executing*, not calendar time |

In `0.4.x` a resumed run started on a **blank ledger**: `RunPersistence.init()`
overwrote `run.json` with zero usage, zero iterations and a new start time, and
the guard started a fresh deadline clock. A run stopped at its cost cap could be
resumed forever, each time with a full new allowance. That is fixed, and it is a
behavior change in the direction of costing you less.

`timeoutMs` measuring active time is what makes a human pause viable at all: an
hour of human thinking is not agent compute, and charging it to a wall clock
would turn every pause into a timeout. **An hour parked costs the run nothing.**
(A fork is the exception, deliberately: it inherits the history but not the
ledger, so it runs on a new budget.)

### What you have to do

| If you... | Then... |
| --- | --- |
| `switch` exhaustively on `WireRunStatus` | Handle `awaiting_input` |
| Call `query({ resumeFromCheckpoint })` | Catch `RunNotResumableError`; use `prepareForkState()` to re-drive a finished run |
| Implement `AgentManagerContract` | Make `cancel` / `cancelAll` return promises |
| Close a review UI on `tool_review_completed` | Use `run_paused` for the pause case |
| Cancel a run that may be **parked** | Call `cancelRun()` — an abort signal reaches nobody once the process has ended |
| Rely on a resumed run getting a fresh budget | It does not. Budgets are lifetime limits; fork if you want a new one |
| Run two workers against one run directory | The lease refuses the second. Against a genuinely shared store, see [Durable Pause §8.2](../sdk/runtime/durable-pause.md#82-the-lease-is-per-namzu-root) |

## What did NOT change

- `defineTool()` signature and semantics.
- Provider-registration APIs (`registerOpenAI`, `registerAnthropic`, etc.).
- Run, iteration, and tool event shapes, apart from: the new optional `error`
  field on `plugin_hook_completed`; the new `plugin_tool_skipped` lifecycle
  event; the new `requestId` / `checkpointId` fields on `tool_review_requested`;
  and the new `tool_execution_uncertain` event. All four are additive. (The
  `run_id` a sub-agent's events *carry* does change — see
  [Section H](#section-h--one-canonical-run-id) — and *when* a pause emits
  `tool_review_completed` changes — see
  [Section I](#section-i--a-paused-run-is-a-state-not-a-completion) — but no
  existing event's shape is broken.)
- Session hierarchy types.
- Non-plugin tool names. A tool you register directly is unaffected by the
  separator change — only *composed* plugin names use `__`.
- Frame content. Sub-agent and advisory payloads now reach the model **verbatim**
  (see below), which is a fidelity improvement, not a break.

## Frames are authenticated rather than escaped

Not a migration item — no consumer API changed — but worth understanding because
it changes what the model sees.

Sub-agent results and advisory blocks are wrapped in
`<task-notification-{nonce}>` / `<advisory-result-{nonce}>` tags carrying a
per-run nonce, and the system prompt states that only nonce-bearing tags are
framework-authored. A sub-agent that emits a closing tag can no longer forge a
frame boundary.

Because the boundary is now the thing an attacker cannot reproduce, the payload
inside a frame is passed through **verbatim** — code, paths, and ampersands
reach the model byte-exact instead of HTML-escaped. Tool names and descriptions
in the prompt catalogue are still escaped: they are metadata, not content the
model has to reproduce.

## What's new

The reliability layer adds no API you must adopt — but see
[Section G](#section-g--retry-is-on-by-default) for the defaults it turns on. Full
detail in [Reliability and Cancellation](../sdk/runtime/reliability.md):

- `ProviderRequestError` and the typed error taxonomy across all seven providers
- `RetryConfig` — bounded retries with jittered backoff, honoring `Retry-After`
  where the provider exposes it (Anthropic, OpenAI, OpenRouter, HTTP; Bedrock,
  Ollama and LM Studio back off on the jittered schedule instead)
- Reactive context-overflow recovery
- `finishReason: 'length'` handling
- `ChatCompletionParams.signal` and `ProviderCapabilities.supportsAbortSignal`
  (`false` for Ollama's non-streaming path, which the vendor SDK cannot cancel)
- A model call is bounded by the run deadline even while in flight: a provider
  that hangs can no longer hold a run open past its `timeoutMs`. For a provider
  that cannot be aborted, the request may still be in flight — the run simply
  stops waiting for it, and its late answer is discarded rather than acted on.
- `repairDanglingMessages()` / `prepareResumeMessages()`
- `BaseAgentConfig.runId` — name the run yourself; the SDK will not rename it
  ([Section H](#section-h--one-canonical-run-id))

The durable pause is the other headline addition — a run that stops for a human
now survives the process it stopped in
([Section I](#section-i--a-paused-run-is-a-state-not-a-completion)). Full detail
in [Durable Pause](../sdk/runtime/durable-pause.md):

- `deferredReviewHandler` — the fail-closed default when `query()` gets no
  `resumeHandler`: a tool review parks the run instead of auto-approving it
- `resumeDecision` / `readPendingDecision` / `cancelDecision` — answer a paused
  decision out of process, against an opaque single-use resume token
- `cancelRun` — cancel a run that may be **parked**, where an abort signal
  reaches nobody
- `readRunLease` — who is driving a run: `free` (parked), `held` (live), or
  `stale` (crashed). Three states, not two
- `prepareForkState` — fork a **new** run from a checkpoint, with provenance.
  Resume continues *the* run; fork mints a new one
- `RunLeaseHeldError`, `RunLeaseLostError`, `RunNotResumableError`,
  `DecisionAlreadyResolvedError`, `DecisionTokenInvalidError`,
  `DecisionNotFoundError`, `DecisionOutcomeInvalidError`,
  `ForkTargetsSourceRunError`
