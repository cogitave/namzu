- **Update** Replace "The write-file size limit" with ["Writing a file larger than one frame"](sdk/kubernetes-sandbox.md#writing-a-file-larger-than-one-frame) (`packages/sandbox/src/backends/firecracker/transport.ts`, `protocol.ts`, `packages/sandbox/agent/agent.cjs`, `packages/sandbox/src/backends/kubernetes/transport.ts`, `sandbox.ts`, `packages/sandbox/src/testing/sandbox-conformance.ts`). `Sandbox.writeFile` used to refuse a body above ~5.9 MiB on the kubernetes backend: every `tcp` request dials a fresh connection and the credential rides inside the envelope, so every request is that connection's first unauthenticated frame and is bounded by the guest's pre-auth ceiling (`NAMZU_AGENT_MAX_PREAUTH_FRAME_BYTES`, 8 MiB) on every call, and a `write-file` carries its whole base64 body in that frame. That page now documents the fix rather than the limit: a body that does not fit one frame is split into parts written to a temporary sibling of the target inside the same workspace jail, each naming the byte offset it starts at (the guest refuses a part whose offset is not the temp file's current size, so a lost, duplicated or reordered part is detected), finished by an atomic rename — so a reader never sees a half-written file, a failed or aborted write leaves the target untouched, and an abandoned sequence removes its temp file best-effort. The guest verifies what it actually wrote before renaming: one `pwrite` answers a write that crosses the volume's free space or an `RLIMIT_FSIZE` with a SHORT count and no error, so the count the syscall returned and the temp file's own size must both match what the part claimed or the part is refused (`write_part_short_write`) with nothing renamed — the final part is the exposure, an earlier one being caught by the next part's offset check. The page also names the one window a cancellation cannot close: a signal that fires after the final rename has landed but before its reply is read rejects a write that did happen. The guest opts in: `agent.cjs` advertises `features: ['write-file-parts']` in its `healthz` reply and the host chunks only for a guest that did, an old guest still getting the named `AgentPreauthFrameTooLargeError` (whose message now names the missing feature). The guest wire protocol version is **unchanged** — `part` is an optional field on an existing op. `part.discard`, the one verb on `write-file` that removes a file, is confined by name to the agent's own `.namzu-write-….part` files (`write_part_not_a_temp_file`, checked lexically as well as on the resolved path, and answering an idempotent success — without creating the directory it would have looked in — when there is nothing there), a `part` that is present but is not an object is refused (`write_part_invalid_shape`) rather than served as the plain whole-file write it resembles, and a final part's `renameTo` is resolved through the workspace jail BEFORE any byte is written, so a refused rename target leaves the temp file untouched. The page also gains the two new `VsockTransportOptions` knobs (`maxWriteFileBytes`, default 1 GiB, checked before the route is chosen so it bounds a single-frame write too, refused with the new `AgentWriteFileTooLargeError`; `writeFilePartBytes`, which the page now also names as the lever for a link slow enough that a part cannot clear the guest's pre-auth deadline), and records that `SANDBOX_CONTRACT_VERSION` moved to `2` because `defineSandboxConformance` gained a large-body case — which exercises the part path on the kubernetes (`tcp`) fixture and the single-frame path on the Firecracker (`unix`) one. `packages/sandbox/README.md`'s protocol section documents the `part` shape and the `features` field beside the pre-auth bounds table. `.changeset/write-large-files-in-parts.md`, **minor** for `@namzu/sandbox` — additive options, additive exports, and a call that used to throw now succeeds.

- **Update** Extend [MCP protocol eras](sdk/mcp-protocol-eras.md#mirroring-tool-parameters-into-headers-x-mcp-header) with `x-mcp-header`: the tool-definition constraints namzu enforces, the `Mcp-Param-*` headers a modern call carries, and the `-32020` recovery (`packages/sdk/src/connector/mcp/x-mcp-header.ts`, `envelope.ts`, `client.ts`). A server may annotate a tool parameter to have its value mirrored into an `Mcp-Param-{name}` request header so an intermediary can route a call without parsing JSON-RPC, and a client on the Streamable HTTP transport must refuse a tool definition whose annotation breaks any of six constraints — non-empty, RFC 9110 `1*tchar`, no CR/LF, case-insensitively unique across the `inputSchema`, applied only to a `string`, `boolean` or `integer` parameter (`number` excluded), and statically reachable from the schema root through `properties` keys alone. `MCPClient.listTools()` now excludes such a tool and logs the name and the reason at `warn`, which is the first place namzu declines to expose something a server offered: the page says so plainly, and says that only annotated tools on that transport can be affected. The page also documents where the validator's subtlety is (it walks the raw schema and never follows a `$ref`, since resolving references first makes a forbidden path look like a permitted one), which connections validate versus mirror (validation follows the transport, as the spec conditions it; the headers follow the era), how a value is written — string as-is, boolean lowercase, integer decimal, then the same base64 sentinel as `Mcp-Name` — and when no header is written at all (an absent or `null` argument, a value whose runtime type contradicts the schema, an integer outside ±(2^53−1)).
