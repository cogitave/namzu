# Documentation update log

## 2026-09-17

- **Update** [Kubernetes sandboxes](sdk/kubernetes-sandbox.md#a-resume-can-bring-the-current-pod-template-with-it): a workspace can now be woken onto the `SandboxTemplate` as it stands today, keeping its disk (`packages/sandbox/src/backends/kubernetes/workspace.ts`, `objects.ts`, `index.ts`). A `Sandbox` carries its own copy of `spec.podTemplate`, taken once in the create `POST`, and agent-sandbox builds every replacement pod from that copy — so a workspace kept for weeks ran the pod spec it was created with, and a new image tag, a memory limit, a `terminationGracePeriodSeconds` or an env entry reached only workspaces created after the edit. The sharp case is a release that changes the agent's wire protocol: every session start runs the privilege probe through an `exec`, the shared execution controller refuses a reservation whose `protocolVersion` is not the host's, and so every adopt and every resume of a workspace pinning the old image failed with `destroy({ deleteDisk: true })` — which takes the disk — as the only exit. `refreshPodTemplate` is opt-in on both entry points (`resume({ refreshPodTemplate: true })`, and `createKubernetesWorkspace(config, { …, refreshPodTemplate: true })` for a restarted host that has no handle) and is honoured on exactly one transition, Suspended → Running. The new section documents the single `application/json-patch+json` body that does it — `test /spec/operatingMode == "Suspended"`, then the annotations, then `/spec/podTemplate`, then `/spec/operatingMode` — why it is a JSON Patch rather than the merge patch every other lifecycle write sends (a merge patch recurses into maps, so a `nodeSelector` entry the template dropped would survive on the object), and that a configured holder epoch's `test` rides in that same body rather than in a second request. It also states what the refresh will not do: never a Running `Sandbox`, because v1.0.2 does not rewrite a pod that already exists, so an adopt that finds it Running and a `test` that loses to another process's resume both bind the pod that is there unchanged and neither is retried; never the disk, because `spec.volumeClaimTemplates` is CEL-immutable and is not in the patch, with two checks before anything is sent (both `KubernetesWorkspaceDiskError`, workspace left `Suspended`) — that the refreshed pod template still claims **this** workspace's disk through `volumeDevices`, and that the template declares no disk this workspace does not have, the second being the one only a refresh can get wrong, since adding a `volumeClaimTemplates` entry with its matching `volumeDevices` entry is a valid edit a new workspace would honour and an existing one cannot have; and never another template, because the label refusal is unconditional while the `runtimeClassName` refusal is lifted only for a call whose patch actually lands and therefore writes the configured class. Two new handle fields, `templateRevision` and `templateCurrent`, read off a new `sandbox.namzu.ai/pod-template-hash` annotation that every create `POST` now stamps, so a host can schedule the suspend-and-resume itself instead of discovering the drift when a release makes the stored image fail every start; a workspace created before the annotation existed reports `undefined` and `false`, because unknown is not current. The page keeps and cites its existing statement that nothing is patched to make a standing object match, now qualified by the explicit opt-in, and `packages/sandbox/k8s/README.md` gains the operator half: a new image tag does not reach an existing workspace on its own. On an object that carries no `metadata.annotations` at all — only a workspace created before this release, since every create now stamps at least the revision — the shared patch builder has to add the map WHOLE, which replaces whatever is there; that operation is now conditioned on `/metadata/resourceVersion` whether or not the call carries a holder epoch, so a refresh cannot erase an annotation another writer stamped in the window (a suspend carrying an epoch onto an already-suspended object writes `metadata` and leaves `spec` alone, which the operating-mode clause cannot see). A refused patch is told apart from a wrong one by re-reading the object, and that re-read can find nothing at all: a workspace deleted in that window surfaces as the gone object it is, on both entry points, rather than as the "another process resumed it first" outcome, which would have sent the caller on to bind a pod that does not exist. **Stays unproven here**: that the sandbox controller builds the replacement pod from `spec.podTemplate` AS REWRITTEN — upstream behaviour, taken from its source; the run that would settle it needs neither a disk nor a workspace (a bare `Sandbox` with any pod template, suspended, sent exactly this patch with a changed image tag, a changed grace period and one `nodeSelector` key dropped, and the replacement pod's own spec read back), and it was attempted and could not be made, because the environment this was written in refuses cluster writes; the `test` clause bounds the cost of the premise being wrong, since a refresh that never reaches the pod is a missed refresh rather than a wrong write, but `templateCurrent` would then report a workspace as current while its pod ran the old spec — and, for the separate reason that it needs block storage, the disk-preserving round trip through a real block-mode PVC (file digests match, PVC uid unchanged). No new RBAC and no guest protocol change; without the option every request is what it always was.

- **Update** [Kubernetes sandboxes](sdk/kubernetes-sandbox.md#bounded-search-and-the-glob-and-grep-builtins): `walkFiles` is implemented on Kubernetes task sandboxes and on `KubernetesWorkspace` (`packages/sandbox/src/backends/kubernetes/sandbox.ts`, `workspace.ts`, `packages/sandbox/src/testing/sandbox-conformance.ts`). The method table on that page previously listed it **Omitted** ("not in this batch"), which cost a host more than one method: the SDK's `glob` and `grep` builtins refuse any sandbox without `walkFiles` and both are in the default builtin set, so a host that registered them and moved from the Firecracker or docker backend to Kubernetes lost both tools with no change on its own side. The implementation adds no wire op and no guest change — it is the SDK's own `walkFilesViaExec` running the SDK's walk program as `node -e` through the existing `execute`, the same enumerator Firecracker and docker use, and the shipped image (`node:22-bookworm-slim`, whose agent is itself node) already had everything it needs. The page now describes what follows from the walk being an execution: it counts as busy for the whole walk rather than per entry, `options.signal` and the consumer's own `iterator.return()` both abort that execution and kill the walk's process group in the guest, a cancellation the guest cannot confirm retires the sandbox exactly as a failed `exec` cancel does (no second rule for walks), and an exhausted examined-entry budget raises `ERR_FILE_WALK_LIMIT` rather than a short list. On a workspace it passes the synchronous `admit()` gate once, when the consumer asks for the first entry, so a suspended workspace refuses a walk exactly as it refuses `readFile` (same class, same `noticedBy: 'admission'`, this operation's own name) and nothing is dialed; admission is not re-checked per entry, so a suspend landing mid-walk fails the walk the way the transport failed and the handle names it a suspension on its next data-plane call, where `admitted()`'s one-shot diagnosis lives. The [conformance section](sdk/kubernetes-sandbox.md#running-the-conformance-suite) records `SANDBOX_CONTRACT_VERSION` moving to `3` for three added sections — `walkFiles`, several `exec` calls at once on one sandbox with no cross-talk between their results, and an `exec` whose `timeout` produces a timed-out result and really terminates the command — and states why the bump strands no deployed guest image: `walkFiles` is optional on `Sandbox` and skips where a backend omits it, and `timeout`/`timedOut` have been on the shared contract and in `agent.cjs` since protocol v2. [File discovery](sdk/file-discovery.md)'s list of adapters built on `walkFilesViaExec` now names Kubernetes beside Docker, ACI and Firecracker. New tests: `backends/kubernetes/__tests__/walk-files.test.ts` (real agent over loopback, real filesystem, including a 12,000-file fixture where breaking out after five entries is proved to leave no walk process in the guest via `/proc`, and a comparison of the `glob`/`grep` builtins against the local provider over the same tree) and `workspace-walk-files.test.ts`. `.changeset/kubernetes-walk-files.md`, **minor** for `@namzu/sandbox` — an optional method a backend did not implement is now implemented, and the conformance suite a backend author runs gained cases.
- **Update** [Kubernetes sandboxes](sdk/kubernetes-sandbox.md#the-lease): a failed lease renewal now retries on a short capped backoff (one second, doubling, capped at whichever is smaller of thirty seconds or a twentieth of the TTL) instead of waiting a full half-TTL for the next attempt (`packages/sandbox/src/backends/kubernetes/lease.ts`). The old cadence made a single failed renewal a coin flip against the object's own `shutdownTime` — the retry and the expiry both landed roughly a TTL after the last success — so one API blip at the wrong moment could delete a live sandbox's pod mid-command. A success still resets the loop to the normal half-TTL cadence; a renewal that finds the object already gone (404/410) still stops the loop immediately. No public API changed.
- **Update** [Kubernetes sandboxes](sdk/kubernetes-sandbox.md#each-shipped-templates-securitycontext): the de-privileged guest agent and every `execute`/terminal child it starts now get a writable `HOME` (`packages/sandbox/k8s/entrypoint.sh`, `k8s/Dockerfile`, `k8s/scripts/capability-check.mjs`). `setpriv --reuid=/--regid=` (the exec both branches end with) changes only the running process's credentials, never the environment, so `HOME` previously stayed `/root` on the root path — a directory #469 already verified the agent uid cannot use, which made LibreOffice without `-env:UserInstallation`, `pip install --user`, npm's cache, and the fontconfig/matplotlib caches all fail against it. `entrypoint.sh` now resolves a writable home once, before EITHER of its two exec sites (the non-root branch and the root branch, both fixed together — a fix to only one would have left the other broken), and exports `HOME`, `USER`, `LOGNAME`, `XDG_CACHE_HOME` and `XDG_CONFIG_HOME` alongside the existing `NAMZU_SANDBOX_WORKSPACE`; `agent.cjs`'s pre-existing, unchanged `childEnvironment` is what actually carries the value into every child, since none of the five is prefixed `NAMZU_AGENT_`/`NAMZU_SANDBOX_`. Resolution order: `getent passwd "$AGENT_UID"` field 6 (the shipped image's own `useradd --create-home` already creates `/home/namzu` owned by the agent uid, so this is the common case) — a missing `getent`, no passwd entry, an entry under `$NAMZU_WORKSPACE_ROOT`, or a directory this uid still cannot be made to own is a fallback trigger, never a failure — then `/tmp/namzu-home-$AGENT_UID` (mode `0700`, owned by the agent uid, never under the workspace root, so it can never appear in `listFiles`/`walkFiles` or an archive). Usability is decided by adopting the directory (create-if-missing, `chown`, then read the result back) rather than by POSIX `-w`, which succeeds vacuously for root on a directory the agent uid cannot write to — precisely the bug this fixes. Only if both the passwd-resolved directory and the `/tmp` fallback are unusable does the pod refuse to start. `k8s/scripts/capability-check.mjs` now also prints `$HOME`, whether it exists, and whether a probe write succeeded, informationally (never failing the check itself), in the same style as its existing `Seccomp` and set-id lines. `k8s/__tests__/entrypoint.test.ts` gains `getent`/`stat` fakes and a `HOME for the guest agent and its children` suite (genuinely-absent `getent`, an unresolvable-then-adopted passwd home, an unowned passwd home falling back, the workspace-root exclusion, and root/non-root parity), plus a `k8s/__tests__/dockerfile.test.ts` check that `useradd` carries `--create-home`; `packages/sandbox/src/backends/kubernetes/__tests__/agent-home-propagation.test.ts` drives the real agent over a loopback socket to prove an unwritable `HOME` fails an `execute` child's own `touch` exactly as before this fix, and a writable one lets both an `execute` and a `terminal` child succeed and report it back — the propagation mechanism itself, which this change does not touch. **Stays unproven here** (no Kata cluster in this environment): whether Kata's guest runtime already populates `HOME` from `/etc/passwd` unaided on the task template's path, and the two application-level acceptance criteria (LibreOffice, `pip install --user`) — neither ships in this image. `.changeset/guest-home.md`, **major** for `@namzu/sandbox` — every task and workspace pod's exported environment now differs from before on the normal (non-error) path, not only in a misconfiguration; a derived image that relied on `HOME=/root` (the only thing running as root before this fix could have depended on) must set `HOME` itself after its own `FROM`.

- **Update** Let a [Kubernetes workspace command outlive the connection watching it](sdk/kubernetes-sandbox.md#a-command-can-outlive-the-connection-watching-it), and make the guest's command-timeout ceiling an operator's knob (`packages/sandbox/agent/agent.cjs`, `packages/sandbox/src/backends/kubernetes/{transport.ts,workspace.ts}`, `packages/sandbox/src/backends/firecracker/{protocol.ts,transport.ts}`, `packages/sandbox/k8s/manifests/sandboxtemplate-workspace.yaml`). A command's output and result were tied to the one host connection that started it: any socket reset made the controller cancel the command, and a cancel it could not confirm in eight seconds retired the pod — so a network blip could cost a workspace every open terminal. If the host process exited instead, nothing cancelled, the command ran on, and its output had been written only to a closed socket and kept nowhere; the only op that returned the record terminated a running command to give it to you. The guest now has ONE retained-output primitive, `OutputLog` — an ordered, size-bounded log of stdout and stderr in a single monotonically increasing byte-offset space, bounded by bytes rather than chunks, whose eviction advances the log's start offset so a read from before it is answered with a `droppedBytes` count — and three additive wire changes read it: `reserve-execution` accepts a caller-chosen `executionId` (reserving one the guest still holds reports its state instead of minting a second reservation, so a retried start runs the command once), `execute` accepts `retainOutput`, and the new `attach-execution` op replays from an offset, follows the live command and ends with one terminal frame. Attach is an observer and nothing else: it never signals the process, closing an attach connection is a no-op, and ending a command stays `cancel-execution`'s job. On the handle, `exec(command, argv, { executionId, detach, detachSignal, reattachWindowMs, onGap })` reattaches from the last offset it received when its connection fails — bounding only getting BACK, and disarming that bound once an attach succeeds — and, if it cannot, rejects with the new `KubernetesExecutionDetachedError` carrying the id and the byte offset to resume from. **It never cancels to reconcile**, so a lost connection now writes nothing to the object at all. New beside it: `attachExecution(executionId, { fromOffset, onOutput, onGap, signal })`, which resolves to the same `SandboxExecResult` and detaches rather than cancels when its signal aborts, and `cancelExecution(executionId)`, the confirmed-cancel path from any process holding the id, which retires nothing when it cannot confirm. A reported gap sets BOTH truncation flags on the result, because the retained log is one interleaved space and the loss cannot be attributed to either stream. The guest advertises `execution-attach` in `healthz` and a host asking for detach against an image without it is refused before the command is admitted — the wire protocol version is deliberately unchanged, as `write-file-parts` left it. Idempotency ends at the retention window and at pod replacement, and the page says so. The guest's 30-minute `MAX_TIMEOUT_MS` was a hard constant while every ownership limit beside it was an environment variable; it now reads `NAMZU_SANDBOX_MAX_TIMEOUT_MS` — the same variable `worker/server.js` has always read for the same limit — defaults to the unchanged 30 minutes, and names the variable in its refusal. Four variables join the workspace template's `env` block at their defaults: that one plus `NAMZU_AGENT_EXECUTION_LOG_BYTES` (1 MiB), `NAMZU_AGENT_MAX_RETAINED_OUTPUT_LOGS` (32) and `NAMZU_AGENT_EXECUTION_RETAINED_TTL_MS` (10 min), which together bound what retention can cost the 512Mi container. `packages/sandbox/README.md`'s protocol section documents the primitive and the ceiling. `SandboxExecOptions` is **untouched** and nothing here reaches the SDK's `Sandbox`, so `@namzu/sdk` needs no changeset. `.changeset/exec-detach-and-reattach.md`, **minor** for `@namzu/sandbox` — every new capability is opt-in, the default exec path is byte-identical on the wire, and the timeout ceiling defaults to the value it has always had.

- **Update** Stop [Kubernetes workspace failure paths](sdk/kubernetes-sandbox.md#nothing-but-an-explicit-delete-deletes) from suspending a workspace that is in use (`packages/sandbox/src/backends/kubernetes/workspace.ts`, `sandbox.ts`, `transport.ts`, `packages/sandbox/src/backends/remote-execution-controller.ts`). Two paths sent an `operatingMode: Suspended` patch that no caller asked for, and that patch makes the controller delete the pod — every terminal, dev server and running command in it, for every holder. (1) A failed create, adopt or resume patched `Suspended` on **any** error, and the errors that reach it include a caller's `signal` aborting during readiness, one 5xx or 429 on a Sandbox or pod GET (the client does not retry) and a privilege probe that overran its deadline — all of which happen to a SECOND process while the first is using the workspace, which is the normal case given that a workspace id is a name and not a lock. A start failure now patches only when this call moved the mode: it POSTed the object, or its `Running` patch took the object out of `Suspended`. `resume()` reads `spec.operatingMode` before patching rather than patching blind, so a resume that finds another process has already woken the workspace sends nothing and binds the pod that is there. The new `onStartFailure` option (`'suspend-if-woken'` by default, `'leave'` to write nothing on any start failure) sits on both `KubernetesWorkspaceOptions` and `KubernetesWorkspaceTransitionOptions`. The inverse case is kept deliberately: a workspace this call woke and then failed to start is suspended again, or it would be left `Running` with a pod nobody is using. (2) An execution whose cancellation could not be confirmed retired the handle, which on a workspace was the same suspend patch — so eight seconds of network loss under one `exec()`, or a pod evicted under an in-flight command, took the pod away from every holder. It now writes nothing at all: the `exec()` still rejects with `RemoteCancellationUnknownError`, now carrying `retirement: { accepted: false, reason: 'workspace-kept' }` (`reason` is a new optional field on `SandboxRetirementObservation`), the handle goes on admitting calls, and one bounded `healthz` over a fresh connection reports through the new `onCancellationUnconfirmed({ error, agent })` callback whether the agent is `'ok'`, has fenced itself (`'retiring'`) or could not be reached (`'unreachable'`) — a distinction the transport's boolean `healthz()` collapses. A host that wants the old behaviour calls `suspend()` from that callback. A reservation refused with `agent_retiring` on the Kubernetes adapter is now `KubernetesAgentRetiringError`, naming `suspend()` then `resume()`, instead of `RemoteProtocolError: remote sandbox returned an invalid execution reservation`; unlike the Firecracker tier's mapping of the same refusal it does not retire the handle. Nothing here adds a DELETE — `deleteDisk: true` and `deleteKubernetesWorkspace` remain the only paths that remove a disk. New on the public surface: `KubernetesWorkspaceStartFailurePolicy`, `KubernetesWorkspaceAgentState`, `KubernetesWorkspaceCancellationNotice`, `KubernetesAgentRetiringError`, `KubernetesWorkspaceOptions.onStartFailure`/`.onCancellationUnconfirmed`, `KubernetesWorkspaceTransitionOptions.onStartFailure` and `SandboxRetirementObservation.reason`. `.changeset/workspace-failure-paths-keep-the-pod.md`, **major** for `@namzu/sandbox` — two observable defaults moved, and the changeset names how to restore each.
- **Update** Read a large file out of a sandbox in bounded memory — [reading a file larger than one frame](sdk/kubernetes-sandbox.md#reading-a-file-larger-than-one-frame) (`packages/sandbox/agent/agent.cjs`, `packages/sandbox/src/backends/firecracker/{transport.ts,protocol.ts,index.ts}`, `packages/sandbox/src/backends/kubernetes/{transport.ts,sandbox.ts,workspace.ts}`, `packages/sandbox/src/backends/{docker,aci-standby-pool}/index.ts`, `packages/sdk/src/types/sandbox/index.ts`, `packages/sdk/src/sandbox/provider/local.ts`, `packages/sandbox/src/testing/sandbox-conformance.ts`). `Sandbox.readFile` took no options and returned the whole file from one request and one reply frame, and the guest built that frame by loading the file, base64-encoding it into one JSON object and writing it — so the file buffer, the base64 string, the JSON string and two frame buffers all existed at once, about 7.7x the file, in the container the workload shares. Measured against the shipped agent over loopback TCP (`VmHWM` of the agent's OWN process; under the shipped image `tini` is PID 1, so `/proc/1` measures the init), a 64 MiB read grew it by **405 MiB** against the workspace template's `512Mi` limit, and a file of about 384 MiB or more could not be read at all — its base64 string is longer than V8 lets a string be. Reads now have two further shapes. `read-file` takes optional `offset`/`length` and `pread`s one slice, answering with the WHOLE file's `sizeBytes` beside it and with the bytes that exist when the range runs past the end; one slice is one frame, so above `NAMZU_AGENT_READ_FILE_RANGE_BYTES` (1 MiB) the guest REFUSES rather than shortening, because a caller that asked for 4 MiB, got 1 MiB and was told nothing would read the short answer as the end of its range. A new authenticated `read-file-stream` op opens the fd once and sends `meta`, then base64 `data` frames, then `end`, then the zero-length terminator — `execute`'s terminated-stream shape — reusing one read buffer and waiting for the socket to drain between chunks, so a 1 GiB read grows the agent by about **12 MiB** at the 256 KiB default chunk (`NAMZU_AGENT_READ_FILE_STREAM_CHUNK_BYTES`; 1 MiB chunks measured 74.5 MiB, above the 64 MiB budget, which is what chose the smaller default at roughly 40% more wall time per gigabyte). A whole-file `readFile(path)` is built on the stream against a guest that advertises the capability, so existing callers lose the ceiling with no code change — the bytes are copied into one allocation sized from the `meta` frame rather than collected and concatenated, since concatenating needs every chunk to exist at once and costs twice the file (2.3x measured on a 256 MiB read, against the 2x it is held to). The guest opts in: `agent.cjs` advertises `read-file-stream` in `healthz` beside `write-file-parts`, ONE string for both read shapes because they ship in the same file; against a guest that does not advertise it a whole-file read takes the unchanged single-frame path and a ranged read or a `readFileStream` throws the new exported `AgentReadFileStreamUnsupportedError` before dialing, because such an agent ignores `offset`/`length` and answers with the whole file, which the caller would read as its slice. The guest wire protocol version is **unchanged**. A regular file whose `stat` reports no size — the procfs/sysfs shape, reachable only through `NAMZU_SANDBOX_READ_ROOTS` — is read to EOF rather than answered as empty on BOTH new shapes: a whole-file read is now served by the stream and `fs.readFile` read those to EOF, and a ranged read reads the file once to get a true size, since every number a range is made of would otherwise come from the zero `stat` gave and the caller would be told the file is empty. A range must ask for `base64` (`read_file_range_requires_base64`), because a `utf8` slice at an arbitrary offset can split a multi-byte character, and the stream serves regular files only (`read_file_stream_not_a_regular_file`), so a whole-file read of a fifo or a device node — which only `NAMZU_SANDBOX_READ_ROOTS` can put within reach — is now refused rather than attempted, and a file that shrinks under the open fd fails the read instead of coming back short. Both new shapes go through the same `resolveReadablePath` + `realpathWithinWorkspace` jail, and on the Kubernetes backend `readFileStream` is rebound to a replaced pod only around its FIRST chunk — a re-dial after bytes have been yielded would restart the file and the consumer would concatenate a duplicate prefix. New on `@namzu/sdk`: `readFile`'s optional second parameter, the optional `readFileStream?` method and `SandboxReadFileOptions`; source-compatible in both directions, since a caller may omit the parameter and a backend may declare the narrower form. `defineSandboxConformance` gains a 9 MiB read and an explicit byte range, gated on the new `supportsRangedAndStreamedReads` option; those two cases deliberately did NOT raise `SANDBOX_CONTRACT_VERSION` any further (`walkFiles`, concurrent `exec` and the `exec` timeout took it from 2 to 3, and none of the three needs a guest feature that did not already exist), because the Firecracker tier's guest lives in a golden rootfs image that is not built from this repository — nothing here builds one and `packages/sandbox/package.json#files` does not ship `agent/` — so a contract bump would assert something about images this repository cannot see; the three suites that DO run this repository's agent set the flag true and every other backend gets the two cases as named, counted skips. `KubernetesWorkspace` forwards `readFile`'s options to the guest and gains `readFileStream`, both narrowed to present and both admitted like every other data-plane call, so a suspended workspace refuses them by name. The three backends that cannot serve a range now REFUSE one instead of ignoring it: the SDK's local provider serves it from one positional read, and the docker and standby-pool workers — whose HTTP `/read-file` has no range — throw, because a backend that takes `offset`/`length` and answers with everything is the silent wrong answer the contract exists to forbid; all three also honour `options.signal`, which the contract documents as aborting the read. `packages/sandbox/README.md`'s protocol section and `k8s/README.md`'s contract-suite step document the new shapes. `.changeset/read-file-ranged-and-streamed.md`, **minor** for `@namzu/sandbox`; `.changeset/sandbox-read-file-options.md`, **minor** for `@namzu/sdk`.

Both verbs record a state only once the cluster has confirmed it — `suspended` after the patch lands AND the pod is observed stopped, `deleted` after the DELETE resolves or reports the object already gone — since each is idempotent by early-returning on that record, and writing it on the way out turns a failed request into a permanent silent success: a `destroy({ deleteDisk: true })` whose DELETE 500s would answer every retry "already deleted" while the Sandbox, its pod and its PVC stood on the cluster, and a `suspend()` whose patch 500s would leave a pod running behind a handle that said it was asleep. A failed request leaves the state it found and rethrows; a second `suspend()` or `destroy()` arriving mid-transition awaits the one in flight, under the first caller's `signal`, rather than sending a second request into the window that deferral opens. `destroy()` stays idempotent across its two shapes as well: a plain `destroy()` on a workspace `destroy({ deleteDisk: true })` already removed is a no-op in either admission order, since `destroy()` is the verb a `finally` block calls, while an explicit `suspend()` on a deleted workspace still throws. Reattaching to an existing object checks that object rather than the caller's intention: the block disk, the `sandbox.namzu.ai/template` pod label (what an egress policy's `podSelector` matches, so an object built from another template is refused even though the policy verified) and `runtimeClassName` when one is configured (the VM boundary, which the privilege probe cannot see go missing) — a disagreement throws `KubernetesWorkspaceMismatchError` before the object is woken or dialed, and nothing is patched to make it match. No failure path deletes, and that includes the one nobody calls: when an execution's cancellation cannot be confirmed — a wedged agent, a partitioned pod — the shared execution controller retires the pod the command was left in, and where a task sandbox is retired by being DELETEd (its object is disposable), a workspace is retired by the same `operatingMode: Suspended` patch, so the `exec()` rejects carrying its `retirement` observation, the workspace reads `suspended: true` and `resume()` brings up a fresh pod on the same disk. Fixes a defect on the task path in the same change: a pool-less `create()` copied the `SandboxTemplate`'s `podTemplate` and dropped its `volumeClaimTemplates`, producing a healthy Sandbox with no disk.
