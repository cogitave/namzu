# A ratchet at zero needs a floor

A ratchet is a number in a file, compared against a count taken from the tree.
It is the right shape while a count is on its way down: the number says what the
tree is today, exact equality means a change in either direction has to touch
the file, and a reviewer sees it move.

The moment the count reaches zero, that shape stops being enough — and it stops
quietly, because nothing about the gate changes on the way past.

## What a ratchet actually asserts

"The tree matches the number." Not "the number is right."

Those are the same claim while the number is a measurement of work in progress.
They come apart the instant zero means *the thing being counted no longer
exists*. At that point the honest assertion is not "the count is 0 and a change
must be declared" but "there is no legal call site, and a count is not how you
make one legal."

## The regeneration hole

Any ratchet worth having comes with a way to re-record it — here, a `--write`
flag that recomputes from the same scan the check runs. That flag is what makes
a ratchet maintainable, and it is exactly what a floored ratchet cannot allow.

The failure runs in three steps, none of which is caught:

1. Someone reintroduces the call site the gate exists to keep out.
2. The gate fails, and its message says to update the file.
3. They run `--write`. The number becomes 1, the tree is 1, the gate is green.

What lands is a one-line JSON diff — `0` to `1` — inside a change that has a
plausible reason for touching that file, because the gate told the author to
touch it. A reviewer reads it as housekeeping. The regression is now recorded
rather than blocked, which is worse than unrecorded: the file says the tree is
correct, and the file is the thing a later reader trusts.

## The rule

**Once a ratchet reaches zero because the counted thing was removed, add a
separate check that fails on any non-zero value in the config — and make the
regeneration path refuse rather than re-record.**

Two properties make it hold:

- **It reads the config, not the tree.** A check that recomputed from the tree
  would be the ratchet again, and `--write` would satisfy it the same way. The
  recorded value is itself the violation, so it survives regeneration.
- **The refusal comes before the write, not after it.** Reporting afterwards
  leaves the file already changed and the author already past the moment they
  would have stopped.

Say which ratchets are floored, and why each reached zero, in the config file —
the number `0` does not distinguish "we finished driving this down" from "we
have not started."

## Where it came from

LOG-20 removed the SDK's process-wide logger, driving
`log-standard.json#getRootLoggerCount` from 1 to 0 and leaving
`unnamespacedBindingCount` at 0 from an earlier task. Both counted things that
no longer exist — one an export that was deleted, one a binding style every call
site had migrated off.

The gate's own header already argued, correctly, that exact equality beats a
ceiling: "a ceiling lets the true count drift upward as long as it stays under
the line, and the gate would report nothing wrong while measuring nothing real."
That argument is about a count in motion. It does not reach the case where the
right answer is fixed, and the file's `--write` flag — added for the same good
reason — is what turned the gap into a working bypass.

Verified by mutation in both directions before it was trusted: a real
reintroduced call site in `packages/sdk/src` fails the gate, and `--write` exits
1 with the config untouched rather than recording the new count.
